# X List 自动监控与 AI Digest 设计规格

## 1. 目标

构建一个单用户、自托管的 X List 监控工具：按固定频率获取指定 X List 中成员的新帖子，进行去重、线程合并、链接正文提取、主题分类和中文 AI 总结，最终通过网页和可选通知渠道提供阅读。

第一版不监控完整 Home Timeline，不自动发帖，不支持多用户 SaaS，也不以绕过 X 访问限制为目标。

## 2. 用户与成功标准

目标用户是希望降低 X 信息噪音、定期阅读精选账号内容的个人用户。

MVP 成功标准：

- 用户可以配置一个或多个 X List。
- 系统可以定时发现新帖子，并避免重复入库。
- 连续 thread 能被合并为一条可读内容。
- 帖子和链接可以生成可追溯的中文摘要。
- 用户可以按 List、作者、主题和日期浏览结果。
- 系统可以生成每日或每 6 小时 digest。
- 原始 X 链接始终保留，摘要失败不会丢失原文。

## 3. 方案选择

采用“采集适配器 + 统一内容模型”的架构。

第一采集器使用官方 X API，优先保证权限边界、稳定性和可维护性。采集器接口保留后续加入浏览器登录态采集器或 RSS 采集器的空间，但这些不作为第一版的隐式绕过手段。

推荐的替代方案对比：

| 方案 | 优点 | 风险 | 决策 |
|---|---|---|---|
| 官方 X API | 稳定、字段明确、合规边界清晰 | 需要开发者账号和额度 | 第一版主方案 |
| 浏览器登录态 | 早期验证快 | 页面变化、登录过期、反爬 | 作为后续适配器 |
| RSSHub/第三方 RSS | 实现成本低 | 外部依赖、延迟、字段不完整 | 仅作为备选 |

## 4. 系统架构

```text
X List 配置
    ↓
采集调度器 ──→ X 采集适配器
                      ↓
                统一帖子模型
                      ↓
        去重 / thread 合并 / 链接提取
                      ↓
              AI 分类与摘要任务
                      ↓
        PostgreSQL/SQLite + Web 阅读界面
                      ↓
               Email / Telegram Digest
```

建议技术栈：Python、FastAPI、SQLAlchemy、PostgreSQL（本地开发可用 SQLite）、APScheduler 或 Celery/RQ、Next.js、Docker Compose。LLM 层使用 OpenAI-compatible 接口，允许切换云模型和本地 Ollama。

## 5. 核心模块

### 5.1 List 管理

- 保存 X List 标识、名称、同步频率、启用状态和上次同步时间。
- 支持手动立即同步。
- 保存同步游标或最后成功时间，避免每次全量抓取。

### 5.2 采集层

采集器输出统一字段：帖子 ID、作者、文本、发布时间、媒体、引用/转发关系、回复关系、链接、原始 URL 和采集时间。

采集层必须支持：

- 请求限流和分页。
- 超时、429、5xx 的指数退避。
- 单次同步的最大帖子数。
- 失败记录和可重试状态。
- 不因单个坏帖子导致整批任务失败。

### 5.3 内容处理层

- 以平台帖子 ID 做幂等去重。
- 对短时间内同一作者的连续回复进行 thread 聚合。
- 识别转发、引用和原帖关系。
- 提取帖子中的外部链接。
- 链接抓取失败时保留帖子本身。
- 标记广告、重复转发和关键词黑名单。

### 5.4 AI 层

AI 处理分为两个阶段：

1. 单条内容处理：摘要、关键观点、语言、主题标签、重要性评分。
2. Digest 处理：将同一时间窗口内的内容按主题聚类，生成整体简报和推荐阅读项。

输出必须结构化，至少包括：

- `summary`
- `key_points`
- `topics`
- `importance`
- `language`
- `source_ids`

AI 失败时保留原文并记录错误，不无限重试；重试次数和模型调用成本需要可配置。

### 5.5 阅读界面

MVP 页面包括：

- Digest 列表和详情。
- 原始帖子流。
- 按 List、作者、主题、日期过滤。
- 摘要与原文并排查看。
- 标记已读、收藏和忽略。
- 手动重新生成摘要。

## 6. 数据模型

核心实体：

- `x_lists`：监控的 List 配置。
- `authors`：作者基本信息。
- `posts`：帖子原文、关系、媒体和时间。
- `post_list_memberships`：帖子与 List 的关联。
- `threads`：聚合后的 thread。
- `links`：外部链接和提取正文状态。
- `summaries`：结构化 AI 输出、模型和版本。
- `digests`：时间窗口、主题分组和生成状态。
- `sync_runs`：每次同步的状态、游标、错误和统计。

所有同步和 AI 任务都应具备幂等键，避免重复计费和重复通知。

## 7. 通知与调度

默认支持网页查看；邮件或 Telegram 作为可选通知渠道。

- 同步任务按 List 配置运行。
- Digest 任务按全局时间窗口运行。
- 通知发送失败可以重试，但不能重复发送同一 digest。
- digest 生成应记录内容版本，重新生成不会覆盖历史版本。

## 8. 安全与合规边界

- API 密钥只通过环境变量或本地密钥配置提供，不写入数据库明文。
- 浏览器登录态适配器如未来加入，凭据必须加密保存，并明确提示登录态过期风险。
- 不实现 CAPTCHA 绕过、权限绕过或批量账号操作。
- 外部链接正文只用于用户配置的摘要流程，不默认公开分享。
- 所有摘要保留来源链接，避免把模型输出误认为原文事实。

## 9. 测试与可观测性

测试重点：

- API 分页、限流、重试和游标推进。
- 同一帖子多 List 出现时的去重。
- thread 顺序和边界判断。
- 链接抓取失败和无正文情况。
- AI 返回无效 JSON、超时和部分失败。
- digest 重复生成与重复通知。

运行状态至少记录：同步成功率、抓取帖子数、去重数、摘要成功率、模型 token/费用估算、任务耗时和最后错误。

## 10. 迭代顺序

1. 单 List、手动同步、帖子入库。
2. 定时同步、幂等去重和基础网页列表。
3. thread 合并、链接提取和单条摘要。
4. 主题聚类、digest 和邮件/Telegram 通知。
5. 多 List、过滤规则、收藏/已读和重试后台。
6. 根据实际稳定性再评估浏览器登录态或 RSS 采集器。

## 11. 明确不在本计划中的内容

- YouTube 或其他平台。
- 多租户、计费和公开注册。
- 自动点赞、转发、发帖或评论。
- 实时毫秒级同步。
- 以非官方方式规避 X 的访问控制。
